# MixControl

Первый запуск на другом Windows-ПК: [START-WINDOWS.md](START-WINDOWS.md).

Запуск, размещение на рабочем сервере и GitHub: [DEPLOYMENT.md](DEPLOYMENT.md).

Веб-приложение для ежедневного контроля температур смесей: React + TypeScript + Tailwind CSS, Node.js / Express и PostgreSQL. Рабочие данные хранятся только в PostgreSQL. Демонстрационные записи автоматически не создаются.

## Локальный запуск

Требуется Node.js 24. Для локального запуска PostgreSQL поставляется с зависимостями проекта.

```powershell
npm ci
npm run dev
```

Интерфейс: http://127.0.0.1:5173. API: http://127.0.0.1:3001. При запуске сервера автоматически применяется идемпотентная схема с блокировкой миграции. Для отдельного обновления схемы: `npm run db:migrate`.

При первом открытии создаётся единственный KEYUSER: имя, уникальный логин и пароль не менее 4 символов. Паролей по умолчанию нет. Первоначальная регистрация закрывается после создания первого пользователя. В существующей базе без KEYUSER миграция 005 назначит эту роль первому активному ADMIN, сохранив логин и пароль; переход фиксируется в аудите.

Команда `npm run dev` проверяет подключение к БД и при стандартном локальном DATABASE_URL автоматически запускает постоянную PostgreSQL из `.postgres/` в этой папке. Если .env отсутствует, он создаётся из .env.example. Уже работающая PostgreSQL используется повторно. Внешняя или нестандартная БД автоматически не подменяется: проверьте DATABASE_URL и запустите её отдельно. Ctrl+C останавливает приложение и только ту локальную БД, которую запустила эта команда; данные остаются на диске. `npm run db:local` сохранена для отдельного ручного запуска БД. Если порт занят предыдущим запуском, завершите его через Ctrl+C. Для диагностики можно временно задать PORT (API) и DEV_WEB_PORT (интерфейс) в терминале.

## Запуск готовой сборки

```powershell
npm run build
npm start
```

Сервер раздаёт собранный интерфейс по http://127.0.0.1:3001. Локальный доступ задан по умолчанию.

## Docker

Установите Docker с Compose, задайте в `.env` переменную `POSTGRES_PASSWORD` (случайный пароль из букв и цифр длиной не менее 24 символов), затем:

```sh
docker compose up --build -d
```

Адрес: http://127.0.0.1:3001. Данные сохраняются в томе `postgres_data`. Не используйте `docker compose down -v`, если хотите сохранить базу. В Docker DATABASE_URL настраивается автоматически; PostgreSQL наружу не опубликован.

## Работа

1. Администратор добавляет смесь через модальное окно: название, T min и T max. Справочник представлен компактной таблицей с поиском и вкладками «В работе» / «Архив».
2. Создайте запись журнала: уникальный SUP из ровно 7 цифр, смесь и температуры T(fact) / T(обор). Дату автоматически задаёт сервер (Europe/Moscow); ручного поля даты нет. При отсутствии T(fact) запись получает статус «Ожидает»; дополнить температуру после сохранения может ADMIN или KEYUSER.
3. Нажмите «Сохранить запись». Сотрудник вводит реальные измерения без показа нормативов и предварительного OK/NOK. Результат появляется после подтверждения и вычисляется PostgreSQL. Администратор сохраняет предпросмотр результата.
4. Используйте поиск, фильтры, сортировку и экспорт в `.xlsx`. Экспорт включает все записи выбранного фильтра независимо от страницы (до 100 000 строк).

**OK:** обе температуры T(fact) и T(обор) находятся в диапазоне T min…T max, включая границы. Отклонение хотя бы одной даёт **NOK**, даже если другая ещё не введена. Без отклонений, но при неполных измерениях — «Ожидает». Температуры конечны и находятся в технических границах −273,15…10 000 °C.

SUP — строка из ровно семи ASCII-цифр, например `0123456`; ведущие нули сохраняются. Пробелы, буквы, шесть или восемь цифр запрещены. Формат проверяется формой, сервером и CHECK в PostgreSQL, уникальность — формой, сервером и ограничением UNIQUE. Конкурентный ввод одинаковых SUP допускает только одну запись, второй запрос получает понятную ошибку 409.

В записи хранятся автор, снимки названия и нормативов. Изменение справочника, архивирование или редактирование фактических значений не обновляют исторические нормативы. При явной смене смеси применяются актуальные нормативы выбранной смеси. Подмена нормативов, результата, роли или автора через тело запроса не влияет на серверные значения. Автор определяется по сессии, а права проверяются на сервере внутри операции редактирования.

Иерархия: **KEYUSER > ADMIN > EMPLOYEE**. KEYUSER управляет журналом, смесями, импортом/экспортом и аккаунтами всех ролей. ADMIN управляет журналом и смесями, импортирует/экспортирует данные, создаёт EMPLOYEE/ADMIN, но изменяет, блокирует и удаляет только EMPLOYEE; управлять ADMIN и KEYUSER или назначать KEYUSER ему запрещено. EMPLOYEE только просматривает журнал, ищет/фильтрует записи и создаёт новые измерения. Даже собственные сохранённые записи сотрудник не может изменить или удалить; экспорт, импорт и полный справочник ему закрыты. Для выбора смеси и фильтра используется отдельный API с названиями без нормативов.

KEYUSER может быть только один, включая отключённые аккаунты: это защищает уникальный индекс PostgreSQL. Последнего активного KEYUSER нельзя отключить или понизить; удалить собственный активный аккаунт нельзя. При удалении пользователя запись мягко помечается удалённой, доступ и сессии отзываются, аккаунт исчезает из списка, а измерения и авторство сохраняются. Перед удалением интерфейс показывает подтверждение. Все ограничения проверяются сервером, а изменения пользователей, смесей, измерений и импорты фиксируются в audit_log. Аудит сохраняет SUP, исполнителя, время, старые/новые данные; пароли и их хеши в аудит не попадают.

Архивные смеси остаются в истории и фильтрах, но недоступны для новых записей. Удалить используемую смесь нельзя благодаря внешнему ключу. Версионирование записей предотвращает потерю изменений при одновременном редактировании или удалении.

У существовавших до авторизации корректных записей автор назначается первому администратору. Миграция не удаляет и не переименовывает исторические записи с SUP старого формата: они остаются доступны администратору для исправления. Новый CHECK запрещает любые новые или изменённые строки с некорректным SUP. Если все старые SUP корректны, ограничение сразу валидируется для всей таблицы. Нормативы и результаты старых записей сохраняются.

Миграция 003 добавляет единое поле `actual`. Совпадающие старые Tmin/Tmax переносятся точно; разные или частично заполненные пары получают отметку «На переносе» с сохранением прежнего результата. Исходные `actual_min` / `actual_max` не удаляются и не переписываются. После согласования ADMIN/KEYUSER может вручную указать единое значение. Excel содержит восемь основных столбцов и отдельный лист исходных измерений при наличии старых данных. Дата создания смеси уже хранится автоматически в `mixtures.created_at`.

## Импорт Excel

Импорт/экспорт журнала и справочника доступен ADMIN и KEYUSER. Перед импортом .xlsx сервер проверяет структуру и каждую строку; интерфейс показывает количество строк, добавлений, обновлений, ошибок и предварительный просмотр. Ошибки содержат номер строки, SUP, смесь из Excel, смесь в базе и причину. При ошибках подтверждение запрещено; исправленный файл можно загрузить повторно.

Журнал: столбцы Дата, SUP, Смесь, T min, T max, T(fact), Итог. T(обор) поддерживается дополнительно. SUP — ровно 7 цифр (ведущие нули храните как текст). Существующий SUP обновляется с сохранением ID и автора только при совпадении названия смеси и её связи с записью; новый SUP добавляется для действующей смеси. Повторы SUP в файле, другая смесь, отсутствующая смесь, некорректная дата, число или диапазон блокируют весь импорт. Дата и нормативы из файла могут обновляться при совпадении SUP + смеси. Значение «Итог» из Excel игнорируется: PostgreSQL рассчитывает результат по обеим температурам. Если T(обор) отсутствует, при обновлении сохраняется прежняя температура, а при создании она остаётся пустой. Исходные старые пары температур не удаляются; неоднозначные значения переносятся только явно.

Справочник: Название смеси, T min, T max, необязательный Статус (В работе / В архиве). Экспорт подходит для обратного импорта. Сопоставление названий не учитывает регистр и пробелы по краям. Обновление сохраняет ID и связи, новые смеси добавляются; исторические нормативы измерений не меняются.

Подтверждение выполняется одной транзакцией с аудитом строк и итоговыми счётчиками. Предпросмотр действует 30 минут и привязан к автору. Перед записью сервер повторно проверяет данные: изменения другим сотрудником после предпросмотра требуют повторной загрузки файла. Повторное подтверждение и конкурентные импорты не создают дубликаты. Ошибка БД откатывает всю операцию. Записи вне файла остаются без изменений. Ограничения файла: 5 МБ, 5000 строк, распакованное содержимое до 30 МБ; формулы и сложные значения в полях данных не принимаются.

## Структура

- `src/` — существующий журнал, формы, отдельные компоненты авторизации, пользователей и таблицы смесей.
- `shared/domain.ts` — типы, правила проверки и схемы валидации.
- `server/auth.ts` — пароли, постоянные сессии и управление пользователями.
- `server/repository.ts` — параметризованные запросы, снимки нормативов и контроль авторства.
- `server/events.ts` — уведомления об изменениях через PostgreSQL LISTEN/NOTIFY и SSE.
- `server/migrations/` — последовательные миграции в транзакции с блокировкой.
- `tests/` — проверки пограничных условий и интеграционные проверки PostgreSQL / API.

## Проверки

```sh
npm test
npm run build
```

`npm run test:integration` требует доступного PostgreSQL и права CREATEDB у тестового подключения DATABASE_URL. Команда создаёт отдельную настоящую базу `mixcontrol_test_<случайный идентификатор>`, запускает изолированный API, проверяет роли, сессии, миграцию старых данных, семь цифр SUP, гонки сохранения, лимит 15 строк, Excel и одновременные уведомления двух клиентов. Рабочая база не изменяется; тестовая база удаляется после проверки. Рабочий сервер запускать для этого не нужно.

Для ручной проверки интерфейса на изолированных данных есть `node scripts/ui-check.mjs`: отдельная база, порт 3002, три синтетических аккаунта; адрес и временный пароль выводятся в терминале. Используйте адрес `http://localhost:3002`, чтобы cookie не пересекались с рабочим приложением на `127.0.0.1`. Команда `stop` в терминале или Ctrl+C останавливает проверку и удаляет только созданную ею тестовую базу. Этот режим не предназначен для хранения рабочих записей.

## Эксплуатация

Пароли хранятся в формате scrypt с индивидуальной случайной солью. В cookie находится случайный токен, в PostgreSQL — только SHA-256 токена. Cookie имеет HttpOnly и SameSite=Strict; срок сессии — 12 часов. Выход, отключение пользователя, смена роли или пароля отзывают соответствующие сессии. Все API данных требуют действующей сессии. Запросы изменения с посторонним Origin отклоняются; попытки входа и частота запросов ограничены. Токены не помещаются в localStorage.

Для совместной работы сотрудники открывают один развёрнутый сервер с одной PostgreSQL. Данные не хранятся в памяти браузера. Для удалённого доступа настройте HTTPS, `COOKIE_SECURE=true`, сетевые ограничения, резервное копирование и мониторинг; измените HOST только для нужного сетевого интерфейса или используйте reverse proxy. Не храните секреты в Git; замените локальные пароли БД. На доверенном reverse proxy задайте `TRUST_PROXY=1` только при одном доверенном прокси. Сервис по умолчанию слушает только loopback; Docker-порт также опубликован только локально.

Для SSE на reverse proxy отключите буферизацию `/api/events` и установите тайм-аут чтения более 30 секунд. PostgreSQL оповещает все экземпляры Node.js об изменениях после commit, каждый процесс использует одно выделенное LISTEN-подключение и общий пул запросов (10 соединений). Открытые клиенты обновляют данные по уведомлениям с объединением близких событий; постоянного опроса таблиц нет. Скрытые вкладки загружают актуальные данные при возвращении. SSE переподключается и перепроверяет сессию не реже одного раза в 5 минут.

Резервное копирование PostgreSQL: `pg_dump -Fc -d "$DATABASE_URL" -f mixcontrol.dump`; восстановление в заранее созданную пустую базу: `pg_restore --no-owner -d "$DATABASE_URL" mixcontrol.dump`. Для Docker используйте `docker compose exec -T db pg_dump -U mixcontrol -d mixcontrol -Fc` с бинарно безопасным сохранением файла (в Windows — PowerShell 7.4+ или утилита резервного копирования). Проверяйте восстановление копий регулярно. Перед изменением схемы выполняйте резервное копирование.

Индексы поддерживают фильтры дат, смесей, статуса и авторов; сервер выдаёт не более 15 записей на страницу, даже при подмене параметров клиентом. Счётчики и страница читаются в одном согласованном снимке PostgreSQL. Поиск по вхождению SUP на очень больших базах потребует дополнительного триграммного индекса; нагрузочное тестирование конкретного объёма данных должно выполняться до промышленного развёртывания.

## Сохранение и перенос данных

Рабочая папка проекта: E:\Проекты\MixControl-2026-11-09-v2. Новые архивы не требуются. Данные PostgreSQL переносите согласованным снимком или pg_dump, не копированием файлов работающего сервера.

Для восстановления на другом компьютере: установите Node.js 24, выполните npm ci, настройте DATABASE_URL в .env на отдельную пустую базу, запустите PostgreSQL (или npm run db:local), затем:

```powershell
npm run db:migrate
node scripts/database-snapshot.mjs restore backups/mixcontrol-data-20261109-v2.json
npm start
```

Снимок сохраняет пользователей с хешами паролей, смеси, измерения (включая старые пары) и журнал аудита. Снимки схем 004–008 можно восстановить в текущую схему 009; корректировки без исходных измерений очищаются с техническим аудитом. Снимок 006 также сохраняет корректировки, комментарии, историю и ежедневные отчёты. Сессии и временные предпросмотры импорта не переносятся: после восстановления войдите заново. Восстановление в непустую базу отклоняется без изменения данных. Для новой копии: node scripts/database-snapshot.mjs export backups/новая-копия.json. Файл назначения не должен существовать.

Миграция 004 добавляет T(обор) без удаления измерений. У старых записей новое поле остаётся пустым — значение не выдумывается. Исторические неоднозначные пары с отметкой «На переносе» сохраняют прежний результат до явного переноса; выход T(обор) за нормы всегда даёт NOK. После переноса результат считается по обеим температурам.

Миграция 005 добавляет мягкое удаление аккаунтов, аудит и временные задания импорта. Существующие измерения не удаляются; ограничение единственного KEYUSER сохраняется.

## Ежедневные отчёты и корректирующие действия

Раздел «Ежедневные отчёты» доступен всем ролям. Сервер самостоятельно проверяет наступление нового дня каждые 60 секунд и сохраняет отчёт за предыдущие календарные сутки по Europe/Moscow. Открытый браузер не нужен; процесс Node.js должен работать. После простоя сервер восстанавливает пропущенные дни, обрабатывая историю порциями. Дата отчёта — первичный ключ, PostgreSQL advisory locks защищают от дублей при нескольких экземплярах сервера. Отчёты содержат общее количество, OK/NOK, ожидающие измерения и NOK / всего × 100 с двумя знаками. Детальная таблица показывает только NOK, по 15 строк.

Общий OK/NOK по-прежнему зависит от **обеих** температур: T(fact) и T(обор) должны находиться в сохранённых нормативах. Выход любой температуры за границы даёт NOK. Отдельно PostgreSQL вычисляет ΔT = |T(fact) − T(обор)| через numeric, чтобы разница 33,2 − 30,2 считалась ровно 3. При ΔT > 3 триггер создаёт одну корректировку на внутренний ID измерения, независимо от OK/NOK. Ровно 3 не создаёт задачу. Изменения API и подтверждённый импорт проходят через ту же логику.

Корректировки доступны только ADMIN и единственному KEYUSER, включая API и Excel-экспорт. В карточке сохраняются статусы «Не в работе», «В работе», «Готово», ответственный, выполненные действия, история изменений с автором/временем. Сохранение карточки защищено версией от перезаписи коллегой. Начальные значения температур сохраняются отдельно. При сохранении температур с ΔT > 3 задача и выполненная работа сохраняются. При изменении температур до ΔT ≤ 3 задача физически удаляется в той же транзакции независимо от статуса, включая архив; удаление фиксируется в техническом аудите. Повторное превышение создаёт новую задачу со статусом «Не в работе». Удаление исходного измерения удаляет связанную корректировку по UUID в той же транзакции, независимо от статуса, с техническим аудитом. Миграция 008 очищает старые корректировки без источника и запрещает их появление внешним ключом PostgreSQL.

Поиск SUP, даты, статус, ответственный и серверная пагинация по 15 строк работают в разделе корректировок. Excel содержит все строки выбранного фильтра (до 100 000), а не только страницу: дата, SUP, смесь, обе температуры, ΔT, статус, ответственный, выполненная работа, создание и завершение. Импорта корректировок нет.

Миграция 006 добавляет таблицы отчётов и корректировок, вычисляемую ΔT и триггеры без удаления измерений и без изменения формулы OK/NOK. Имеющиеся расхождения получают задачи. После изменения или удаления исходных измерений соответствующий день помечается для обновления отчёта; серверный обработчик либо открытие отчёта пересчитывает его с записью версии и аудита. Повторное чтение неизменённого отчёта использует сохранённые данные.

Миграция 007 добавляет жизненный цикл корректировок и индексы активных/архивных страниц, не удаляя существующие измерения или сохранённые комментарии. Комментарии убраны из интерфейса и ответов API, создание через прежний endpoint отклоняется с 410. До миграции 009 при удалении корректировки сохранялись отсоединённые комментарии. По актуальному требованию миграция 009 очищает такие остатки; последующие удаления каскадно удаляют комментарии и историю карточки, сохраняя технический аудит.

Вкладка «Активные» содержит NOT_STARTED и IN_PROGRESS, «Архив» — DONE. Повторное открытие DONE возвращает запись в активные; дата завершения очищается, история сохраняется. Обе вкладки используют серверные фильтры и страницы по 15; Excel учитывает вкладку и все фильтры. Кнопка истории открывает отдельное окно, строка открывает карточку мышью либо Enter/Space.

Счётчик у базы смесей удалён. Счётчик корректировок запрашивается отдельным агрегатным API и показывает все незавершённые задачи независимо от фильтров страницы. При нуле скрывается. Изменения, завершение, повторное открытие и автоматическое удаление уведомляют все сессии через существующий PostgreSQL LISTEN/NOTIFY и SSE. EMPLOYEE не получает этот счётчик и доступ к разделу.

### Удаление записей по фильтрам

В журнале ADMIN и KEYUSER могут выбрать даты (границы включены), SUP, смесь и результат, затем нажать «Удалить по фильтрам». Предпросмотр показывает количество со всех страниц и выбранные условия. После подтверждения измерения и связанные активные/архивные корректировки удаляются одной транзакцией с техническим аудитом; остальные записи сохраняются. Без фильтров удаление запрещено. Если подходящие записи изменились после предпросмотра, необходимо повторно открыть подтверждение. При необходимости сначала выполните экспорт Excel.
